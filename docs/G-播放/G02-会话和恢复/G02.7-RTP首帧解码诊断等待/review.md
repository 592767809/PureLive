# G02.7 RTP 首帧解码诊断等待

5.4.15 第三私有候选的同源 K90 普通 profile 包出现：视频计数923→982，但仍覆盖“当前播放器解码失败”。Info 日志确认首帧未到达，约1.4秒和2.9秒两次 video_decoder_runtime，软件回退后 video=none；稍后正常图像无法撤销已发出的错误。相同 PPS 初始等待序列在未修改的默认 NativeDiagnosticGate 离线复现2秒前误报。HTTP MP4 切换健康，Linux 同源正式 RTP 也有变化画面；均不能覆盖 Android 首帧时序。

仅 RTP 为首次音/视频输出前的非致命解码诊断设置5秒有界窗口，重复日志不延期。匹配的视频/音频输出取消对应等待；音频不能代替缺失的视频。首帧后继续原1.2秒运行期窗口，致命输入/不支持解码仍立即上报；换源清空窗口和旧等待。容器选择仍由 G02.6 保持原 RTP URL、MPEG-TS 格式及其他协议清空，第三方媒体库不新增修改。

允许：packages/live_player 的 diagnostics.dart、mpv_input.dart、mpv_engine.dart、对应测试及文档。默认 HTTP/HLS/RTSP/文件行为不变，不全局静默原生日志，不更换内核，不掩盖真正无画面的失败。代码与测试记录范围独立于首帧时序的原机验收。

验证：六项虚拟时间检查覆盖初始恢复、超时、重复日志、首帧后故障、立即致命错误和换源；相关包完整测试及分析。正常 K90 预检至少三次冷启动、同播放器重载、RTP→MP4→RTP，逐对查看变化帧与本次固定播放日志，不能以变化图像掩盖错误遮罩。临时仅在 v4dev 打开本地日志（原为关、Info），全部测试后恢复。之后完整all/14与最终同源十包、最终原生检查，不复用前三轮发行包。

原运营商组播和 Apple 真机仍未验证。所有前三轮失败及候选资产独立保留，尚未公开5.4.15。
